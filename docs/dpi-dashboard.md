# Роутерный DPI-дашборд — спецификация реализации

Самодостаточное руководство по реализации мониторинга DPI-интерференции (РКН/ТСПУ)
на роутере с VPN-туннелем. Реализовано в KVASEC (веб-монитор `http://<router>:8085/`,
вкладка «Дашборд»); этот документ описывает как воспроизвести с нуля.

## Цель

Визуализировать вмешательство DPI в VPN-трафик в реальном времени и за 24 часа.
Метрика — **RX-дропы на приёмной стороне туннеля**: пакеты, которые DPI испортил на
пути и которые не прошли расшифровку/аутентификацию AmneziaWG/WireGuard.

## ⚠️ Критическое проектное решение

**Метрику снимать на роутере (клиентская сторона туннеля), а НЕ на сервере.**

DPI портит пакеты на пути *к* клиенту, поэтому на входном интерфейсе сервера (`awg0`)
дропов нет — всегда 0. Битые пакеты видны только на приёме роутера (`opkgtunNN` или
клиентский WG-интерфейс). Это неочевидно и является главной причиной, почему наивная
серверная реализация бесполезна: `/sys/class/net/awg0/statistics/rx_dropped` на сервере
показывает 0, даже когда DPI активно троттлит.

## Среда

- Роутер: BusyBox/Entware (`ash`, не bash), туннельный интерфейс `opkgtunNN` (или `wgN`)
- Веб-морда: stateless CGI (нет постоянного процесса → историю собирает cron)
- cron с форматом `min hour dom mon dow user cmd`

## Архитектура — 3 компонента

```
[cron: сборщик раз в минуту] → [файл-история JSONL] → [CGI dpi_history] → [canvas-график]
                                        │
                     [CGI tunnel_dpi мгновенные] → [текущие цифры + светофор]
```

## Компонент 1: Сборщик истории (cron-скрипт)

Запускается **раз в минуту**. Читает счётчики, считает дельту от прошлого замера,
пишет точку в кольцевой буфер.

```sh
#!/bin/sh
IFACE=$(sed -n 's/^INFACE_ENT=//p' /opt/etc/kvas.conf 2>/dev/null | tr -d ' \r')
[ -z "${IFACE}" ] && IFACE=opkgtun10
STAT="/sys/class/net/${IFACE}/statistics"
HIST=/opt/tmp/dpi-history.jsonl       # кольцевой буфер точек
PREV=/opt/tmp/dpi-history.prev        # прошлый замер для дельты
MAX=1440                              # 1440 точек = 24 часа

[ -d "${STAT}" ] || exit 0            # туннель не поднят — молча выходим
drop=$(cat "${STAT}/rx_dropped" 2>/dev/null || echo 0)
pkts=$(cat "${STAT}/rx_packets" 2>/dev/null || echo 0)
now=$(date +%s)

rate=0; loss=0
if [ -f "${PREV}" ]; then
    read -r p_drop p_pkts p_time < "${PREV}"
    # ГАРД: битый/частичный prev → пустая арифметика молча роняет busybox
    if echo "${p_drop} ${p_pkts} ${p_time}" | grep -qE '^[0-9]+ [0-9]+ [0-9]+$'; then
        dd=$((drop - p_drop)); dp=$((pkts - p_pkts)); dt=$((now - p_time))
        if [ "${dd}" -ge 0 ] && [ "${dt}" -gt 0 ]; then   # dd<0 = счётчик сброшен (реконнект)
            rate=$((dd * 60 / dt))                         # нормализация на минуту
            [ $((dp + dd)) -gt 0 ] && loss=$((dd * 100 / (dp + dd)))
        fi
    fi
fi
echo "${drop} ${pkts} ${now}" > "${PREV}"
echo "{\"t\":${now},\"rate\":${rate},\"loss\":${loss}}" >> "${HIST}"

# кольцевой буфер — обрезка до MAX
if [ "$(wc -l < "${HIST}" 2>/dev/null || echo 0)" -gt "${MAX}" ]; then
    tail -n "${MAX}" "${HIST}" > "${HIST}.tmp" && mv -f "${HIST}.tmp" "${HIST}"
fi
```

**Подводные камни:**
- `dt` считать реально (`now - p_time`), не хардкодить 60 — если cron пропустил такт,
  нормализация останется верной.
- `dd < 0` = счётчик обнулился при реконнекте туннеля → точку в ноль, не в отрицательное.
- **Гард на числовой формат prev обязателен**: обрыв записи → пустые переменные →
  `$((5 - ))` роняет ash, cron молча перестаёт писать точки (тихий отказ сбора).

**Регистрация cron (идемпотентно, в postinst/установщике):**
```sh
grep -q 'dpi_history.sh' /opt/etc/crontab || \
  echo '* * * * * root /opt/apps/.../dpi_history.sh' >> /opt/etc/crontab
/opt/etc/init.d/S10cron restart
```

## Компонент 2: Backend CGI (2 endpoint'а)

### `tunnel_dpi` — мгновенные метрики

Свой prev-файл (`/tmp/kvas_dpi_prev`), окно = интервал опроса браузера (~3 сек).
Логика дельты идентична сборщику (**тот же гард на формат prev!**). Плюс handshake age.

```sh
# читает rx_dropped/rx_packets → дельта от /tmp/kvas_dpi_prev
# handshake: awg show $IFACE latest-handshakes → now - timestamp
# отдаёт:
{"ok":true,"up":true,"drops_total":N,"drops_per_min":N,"loss_pct":N,"handshake_age":N}
# если туннель не поднят:
{"ok":true,"up":false}
```

### `dpi_history` — весь буфер как JSON-массив

Строки JSONL склеить запятыми (последняя без хвостовой запятой):
```sh
if [ -s "${HIST}" ]; then
    printf '{"ok":true,"points":['
    awk 'NR>1{printf ","} {printf "%s",$0}' "${HIST}"
    printf ']}\n'
else
    echo '{"ok":true,"points":[]}'
fi
```

## Компонент 3: Frontend (canvas-график + светофор)

### Опрос
- Текущие метрики — `tunnel_dpi` каждые **3 сек**
- График — `dpi_history` раз в **60 сек** (чаще нет смысла — точка раз в минуту)
- Таймеры запускать при открытии вкладки, останавливать при уходе (не жечь CPU)

### Светофор (пороги калибровать по реальному фону, НЕ по нулю)
```js
if (rate <= 5 && loss < 1)        led = '🟢 чисто, DPI не мешает';
else if (rate <= 30 && loss <= 5) led = '🟡 лёгкая интерференция';
else                              led = '🔴 активная блокировка / троттлинг';
```
Пороги 5/30 и 1%/5% подобраны эмпирически: на «чистом» порту фон ~0.7 дропа/мин при
0% потерь. Если ставить порог на 0, светофор жёлтеет от фонового шума и бесполезен.

### Canvas-график
Линия данных + горизонтальные **пороговые линии** (пунктир: 5/30 для rate, 1%/5% для
loss) — чтобы визуально было видно «много/мало». Ключевой нюанс масштаба:
```js
// maxY должен учитывать нижний порог, иначе при спокойных данных (у нуля)
// пороговая линия уйдёт за экран и ориентир пропадёт
maxY = Math.max(dataMax * 1.15, нижнийПорог * 1.4, 1);
// верхний порог не рисуем, если он выше шкалы (thr.value > maxY) — данные спокойные
```
Ось X — метки времени из реальных `t` точек («сейчас», «-1ч», «-6ч»...).

## Смысл двух метрик

- **rate (дропов/мин)** — абсолютная интенсивность порчи. Растёт и от объёма трафика,
  и от DPI.
- **loss (% битых)** — доля испорченных от общего потока. **Именно этот показатель
  отличает DPI-троттлинг от простого объёма**: если растёт только rate при loss≈0 —
  это просто много трафика; если растёт loss — DPI активно вмешивается в поток.

## Что показывает на практике

DPI-троттлинг видео (Instagram Reels, YouTube) проявляется **вспышками**: заход на
тяжёлый видео-поток → всплеск rate до сотен/мин и loss до 7–14% на несколько минут →
затем спад к нулю. ТСПУ засекает bulk-профиль потока (крупные пакеты, высокий bitrate)
даже через обфусцированный туннель — обфускация прячет *протокол*, но не *профиль
трафика*. Смена порта на 443/UDP снижает фон в ~120 раз, но не убирает троттлинг
видео по паттерну (для этого — усиление junk/padding в AmneziaWG или AmneziaWG 2.0).
